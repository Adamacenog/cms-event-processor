# Development and container setup

## Configuration

The production host is `CmsEventProcessor/CmsEventProcessor.csproj`; its published entry point is `CmsEventProcessor.dll`. API, Application, Domain, and Infrastructure are folders within that project. Unit and integration tests remain separate projects.

The application loads normal ASP.NET Core configuration, optional `appsettings.Local.json`, development user secrets, then environment variables and command-line overrides. Environment variables use double underscores, for example `Authentication__Accounts__0__PasswordHash`. Supply a complete, validated set of accounts when deploying; configuration arrays merge by index, so avoid accidentally combining stale local accounts with deployment overrides. Deployment images exclude local credential files.

The external JSON shape stays the same: Infrastructure binds account definitions from `Authentication:Accounts`, while the API independently binds its transport option from `Authentication:AllowInsecureLoopbackHttp`. Shared Application models contain no stored hash. The API's web and command adapters use the same Infrastructure registration through Application contracts; initialization can run before any accounts exist because command mode does not start the host or run web startup validation.

Account definitions contain `Username`, `PasswordHash`, and `Kind` (`Cms`, `Reader`, or `Admin`). At least one account of each kind is required, usernames must be globally unique and contain 10-20 ASCII letters/digits/underscores/hyphens, and hashes must use the bounded Identity V3 format generated by setup. The [example file](examples/authentication.example.json) is a shape reference with deliberately unusable placeholders.

Use the [README setup commands](../README.md#running-locally) to initialize accounts. Setup refuses existing files, preserves unrelated JSON settings when adding/rotating, and writes through a temporary file before replacement. Unix credential files are owner-readable/writable only. The API snapshots accounts at startup; changing configuration does not change active credentials until restart.

Production rejects plain HTTP. The development profile explicitly permits loopback HTTP; even with that option enabled, a non-loopback socket peer is rejected. Forwarded headers are not trusted. A reverse proxy requires a future explicit trusted-proxy configuration or end-to-end HTTPS; do not disable transport checks to expose a demo.

## SQL configuration and migrations

Configure both Persistence:WriteConnectionString and Persistence:ReadConnectionString privately before starting the web host. Startup validates their shape without connecting or migrating. Account commands remain independent of SQL. Follow the [SQL guide](persistence.md) for Compose, explicit EF migration commands, runtime privileges, processing budgets, and external test-server configuration.

## Container build and HTTPS execution

From the repository root:

```sh
docker build --tag cms-event-processor:local .
```

The image uses the pinned .NET SDK/runtime, locked dependencies, and a non-root runtime user. It includes neither test controllers nor local credential files. Starting it without account configuration intentionally fails validation.

To run it, provide the generated account file and a development HTTPS certificate as read-only mounts. Create the ignored `.secrets` directory first (`mkdir .secrets`), then export the certificate using `dotnet dev-certs https --export-path .secrets/https.pfx --password <certificate-password>`; replace the placeholder with a private value. Save the certificate settings in ignored `.secrets/container.env`:

```text
ASPNETCORE_URLS=https://+:8443
Persistence__WriteConnectionString=<private write connection>
Persistence__ReadConnectionString=<private read connection>
Kestrel__Certificates__Default__Path=/run/secrets/https.pfx
Kestrel__Certificates__Default__Password=<certificate-password>
```

For the supplied SQL Compose service, join its network with --network cms-event-processor_default and use Server=sql,1433 in both private connections. For an external SQL server, use its address and omit the Compose network option. Replace both path placeholders with absolute host paths, and keep the environment file private:

```sh
docker run --rm --network cms-event-processor_default --publish 127.0.0.1:8443:8443 --env-file .secrets/container.env --mount type=bind,source=<absolute-account-file>,target=/app/appsettings.Local.json,readonly --mount type=bind,source=<absolute-certificate-file>,target=/run/secrets/https.pfx,readonly cms-event-processor:local
```

On Linux, owner-only host files may require running the container with the host user's UID/GID using `--user "$(id -u):$(id -g)" --env HOME=/tmp` so it can read the mounts and has a writable home for framework services. Preserve restrictive permissions rather than making secrets world-readable. Windows/macOS bind-mount behavior depends on Docker Desktop's file-sharing configuration.

Access `https://localhost:8443`. Trust the development certificate using your platform's development-certificate workflow when necessary. This is development setup; a shared deployment needs an appropriately trusted certificate and deployment-managed secrets.

## Operational configuration

The [operations guide](operations.md) documents the protected probes, validated budgets, actual-peer request limit, optional OTLP collector configuration, and graceful shutdown. Export is off by default. Use private configuration or environment overrides; run migrations explicitly before expecting ready status. Configure a platform termination grace period longer than the host shutdown budget. The reproducible load script needs Python 3.10+ and privately supplied CMS credentials.

## Verification boundaries

Unit and HTTP foundation suites do not require SQL Server or Docker when filtered with "Category!=Sql". The HTTP suite validates the actual pipeline through `WebApplicationFactory`, while only the test assembly supplies probe controllers. These checks alone do not establish SQL transaction behavior. The SQL cases require Docker or CMS_TEST_SQL_CONNECTION and separately verify transactions, migrations, and failure behavior, as documented in the [SQL test guide](persistence.md#test-execution-and-evidence). Use the [manual Postman walkthrough](postman/README.md) to check a running native or container instance. [Cloud deployment](deployment.md) remains an optional proposal; it is not claimed as tested.
